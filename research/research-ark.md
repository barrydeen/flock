# Ark Protocol Family — State of Play, mid-2026

## 1. Core mechanics

- **vTXOs**: virtual transaction outputs — chains of pre-signed, off-chain transactions that let the holder unilaterally create a real UTXO later. Held by users, never broadcast unless exiting ([second.tech/docs/learn/intro](https://second.tech/docs/learn/intro), [bitcoinops.org/en/topics/ark](https://bitcoinops.org/en/topics/ark/)).
- **Rounds**: the operator ("Ark server"/ASP) periodically batches users into a single on-chain **round/commitment transaction** whose output funds a **vTXO tree**; each leaf is one user's "exit transaction." Second targets ~1 round/hour; earlier proposals ranged from seconds to minutes ([second.tech/docs/learn/intro](https://second.tech/docs/learn/intro), [spark.money research, Feb 2026](https://www.spark.money/research/ark-protocol-explained)).
- **Forfeits & connectors**: when refreshing/offboarding, users hand the server pre-signed **forfeit transactions** giving it the old vTXO. Atomicity classically comes from **connector outputs** in the round transaction: the forfeit spends a connector, so it is only valid if the new round/payment transaction confirms ([ark-protocol.org/intro/connectors](https://ark-protocol.org/intro/connectors/index.html)). In Bark's current design, refresh atomicity instead uses **hash-locks** (server preimage gates both the new vTXO and the forfeit), with connectors retained for on-chain payments/offboards; exits carry a ~10-hour CSV delay so the server can broadcast a forfeit against a malicious exit ([second.tech/docs/learn/forfeits](https://second.tech/docs/learn/forfeits)).
- **Expiry & refresh**: every vTXO carries an absolute timelock (~30 days at Second; "four weeks" in older proposals) after which the server sweeps the whole round in one transaction. Users must **refresh** (forfeit old vTXO for a new one in a later round) before expiry or the server can also claim the funds ([second.tech/docs/learn/intro](https://second.tech/docs/learn/intro), [bitcoinops.org/en/topics/ark](https://bitcoinops.org/en/topics/ark/)).
- **Boarding**: a user co-signs a funding transaction with the server into a 2-of-2 boarding output (with a user timeout path), confirmed on-chain, later converted into a vTXO via a round. Receiving does **not** require boarding — new users can receive vTXOs immediately ([second.tech/docs/learn/intro](https://second.tech/docs/learn/intro)).

## 2. Covenant-less Ark (clArk)

- Original Ark assumed a covenant (e.g., CTV) so the tree is self-enforcing. **clArk** replaces this with an n-of-n **pre-signed "pseudo-covenant"**: the server plus all round participants cosign every tree transaction (MuSig2), then **delete their signing keys**; security holds if at least one cosigner deletes ([ark-protocol.org/intro/clark](https://ark-protocol.org/intro/clark/index.html)).
- **Interactivity demanded per round**: each participant must be online for the whole ceremony — register inputs/intents, exchange MuSig2 nonces, validate the proposed tree (their leaf and cosigner key included), produce partial signatures over tree transactions (originally the *entire* tree; arkd v0.5, Feb 2025, reduced this to branch-only signing sessions), then sign forfeits ([arkade-os/arkd v0.5.0](https://github.com/arkade-os/arkd/releases/tag/v0.5.0), [ark-protocol.org/intro/clark](https://ark-protocol.org/intro/clark/index.html)).
- If any participant stalls, the **round fails and restarts** for everyone. Steven Roose's Delving post argues receivers are especially dangerous: with no existing vTXO to forfeit, a receiver "can't be penalized and [has] nothing to lose in performing a DoS attack," so in practice clArk rounds are restricted to **self-refreshes** (sender = receiver), and round-based sends/Lightning receives via rounds are avoided ([delvingbitcoin.org "The Ark case for CTV"](https://delvingbitcoin.org/t/the-ark-case-for-ctv/1528)).

## 3. Out-of-round transfers (arkoor)

- **Mechanics**: sender + server cosign a new transaction spending the sender's vTXO leaf to the receiver, creating a "spend vTXO" chained off the original tree — instant, no round, no operator liquidity consumed ([second.tech/docs/learn/payments](https://second.tech/docs/learn/payments)).
- **Trust model until refresh**: the server (not consensus) prevents double-spends, so the receiver must assume **sender and server don't collude**; one honest party suffices. The vTXO is still unilaterally exitable. Exposure is bounded by expiry (~30 days) and ends when the receiver **refreshes** in a round, restoring the standard model. Chained arkoor payments extend trust to *every* prior sender and add one exit transaction per hop; wallets are expected to cap chain depth. Double-spends are detectable when conflicting recipients try to refresh/exit ([second.tech/docs/learn/payments](https://second.tech/docs/learn/payments), [second.tech/docs/learn/vtxo](https://docs.second.tech/ark-protocol/vtxo/)).

## 4. Implementations & deployment (mid-2026)

- **Second (Bark)**: launched on **Bitcoin mainnet June 9, 2026** — Rust SDK (Kotlin/Swift/RN/Flutter/Go/Python/WASM bindings), `barkd` daemon, BTCPay plugin, four mainnet apps; $5.1M raised, 11-person team, CEO Steven Roose ([bitcoinmagazine.com](https://bitcoinmagazine.com/news/second-launches-bark-on-bitcoin-mainnet), [github.com/ark-bitcoin/bark](https://github.com/ark-bitcoin/bark)). An earlier bark mainnet demo dates to 2024 ([bitcoinops.org](https://bitcoinops.org/en/topics/ark/)).
- **Ark Labs / Arkade**: `arkd` server ([github.com/arkade-os/arkd](https://github.com/arkade-os/arkd)); **Arkade** mainnet public beta launched **Oct 21, 2025** (Lugano), adding Arkade Script, TS/Go/Rust SDKs, Arkade Assets (planned USDT), integrations with Boltz, Breez, Bull Bitcoin, BTCPay ([atlas21.com](https://atlas21.com/arkade-activation-day-the-new-layer-2-from-ark-labs-debuts/), [theblock.co](https://www.theblock.co/post/375271/ark-labs-arkade-public-beta-layer-2-bitcoin)).
- **Soft-fork-dependent variants** (designs, not deployable): **Erk** (CTV+CSFS, rebindable signatures → zero round interactivity, perpetual offline refresh; unveiled Apr 2025) and **hArk** (CTV-only, hash-lock rounds; software released 2026 per Optech) ([roose.io](https://roose.io/blog/hark-erk-evolving-the-ark-protocol-using-ctv-and-csfs/), [blog.second.tech/erk-update](https://blog.second.tech/erk-update/), [bitcoinops.org](https://bitcoinops.org/en/topics/ark/)).

## 5. Unilateral exit cost

- Exit = broadcast every tree transaction from root to your leaf, sequentially with confirmations, then (Bark) a claim transaction after the CSV delay; user pays all fees, via P2A anchors + CPFP under Core 28 policies. Arkoor vTXOs add one transaction per chain hop ([second.tech/docs/learn/exit](https://second.tech/docs/learn/exit)).
- Scale: a 1,024-leaf **binary** tree ⇒ ~10 transactions; binary unrolling carries ~100% vbyte overhead for the first exiter (~50% if fully unrolled), so Bark uses **quad (radix-4) trees** to cut depth ([spark.money](https://www.spark.money/research/ark-protocol-explained), [docs.second.tech/ark-protocol/vtxo](https://docs.second.tech/ark-protocol/vtxo/)). No implementation publishes canonical per-exit vbyte totals; small vTXOs can cost more to exit than they're worth. Early exiters subsidize later ones (shared branches already confirmed) ([second.tech/docs/learn/exit](https://second.tech/docs/learn/exit)).

## 6. Operator liquidity & recycling

- The operator **fronts the full value of all new vTXOs each round** and recovers capital only when old rounds expire (~30 days) and are swept in one transaction — so capital turns over per expiry window. Illustrative: 10,000 users × 100k sats ⇒ ~10 BTC active liquidity plus overlap buffer ([spark.money](https://www.spark.money/research/ark-protocol-explained), [docs.arklabs.xyz/ark.pdf](https://docs.arklabs.xyz/ark.pdf)).
- Arkoor payments need **zero** operator liquidity; refresh fees price the cost-of-capital for the new vTXO's remaining lifetime (refreshing early costs more), pushing users toward late refresh ([second.tech/docs/learn/intro](https://second.tech/docs/learn/intro)).

## 7. Criticisms & open problems

- **Round liveness/DoS**: clArk rounds fail if any cosigner stalls; mitigated by branch-only signing and restricting rounds to refreshes, fully fixed only by covenants (CTV) ([delvingbitcoin.org](https://delvingbitcoin.org/t/the-ark-case-for-ctv/1528)).
- **Operator as SPOF**: single coordinator for rounds, arkoor cosigning, and liquidity; if it halts, no refreshes occur and users must exit before expiry ([spark.money](https://www.spark.money/research/ark-protocol-explained), [bitcoinmagazine.com (2023, older analysis)](https://bitcoinmagazine.com/technical/bitcoin-layer-2-ark)).
- **Mass exit**: simultaneous exits ⇒ on-chain volume proportional to tree depth × users; fee spikes could price out small vTXOs entirely ([spark.money](https://www.spark.money/research/ark-protocol-explained), [docs.arklabs.xyz/ark.pdf](https://docs.arklabs.xyz/ark.pdf)).
- **Expiry-based fund loss**: miss every round for ~30 days and the server can sweep your coins — a genuine user-side liveness requirement; Erk/watchtowers are the proposed fix but need CTV+CSFS ([bitcoinops.org](https://bitcoinops.org/en/topics/ark/), [blog.second.tech/erk-update](https://blog.second.tech/erk-update/)).
- **Receiver-side trust/interactivity**: arkoor receivers bear sender+server collusion risk until refresh; round-based non-interactive receive awaits covenants ([second.tech/docs/learn/payments](https://second.tech/docs/learn/payments), [delvingbitcoin.org](https://delvingbitcoin.org/t/the-ark-case-for-ctv/1528)).

*Caveats: parameter values (30-day expiry, hourly rounds, radix-4) are Second/Bark defaults and configurable; the 10-BTC liquidity figure is an illustrative estimate; the original Ark whitepaper and Bitcoin Magazine critique predate 2025-26 designs (hash-lock forfeits, branch-only signing) and overstate some interactivity costs.*
