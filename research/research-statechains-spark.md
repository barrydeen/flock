# Statechain-Based Bitcoin L2s — Status Report (2026-06-12)

## 1) Mercury Layer (CommerceBlock)

- **History.** Statechains proposed by Ruben Somsen (2018–19): transfer a UTXO off-chain by handing over a key, co-signed by an operator ([bitcoinmagazine.com](https://bitcoinmagazine.com/technical/statechains-sending-keys-not-coins-to-scale-bitcoin-off-chain)). CommerceBlock shipped the first production version (Mercury Wallet, 2021; [blog.commerceblock.com](https://blog.commerceblock.com/first-release-mercury-wallet-e1e7d94e457f)), then **Mercury Layer** (Jan 2024), a library/CLI rewrite adding *blinded* co-signing — the single server signs without seeing transactions or statechain IDs ([nobsbitcoin.com](https://www.nobsbitcoin.com/mercury-layer-released/), [bitcoinmagazine.com](https://bitcoinmagazine.com/technical/mercury-layer-a-massive-improvement-on-statechains)).
- **Mechanics.** 2-of-2 keyshares (user + server) over a Taproot UTXO; each transfer creates new shares plus a pre-signed backup/exit tx with a **decrementing timelock** so the newest owner can exit first; server then deletes the old share. Keyshares optionally held in an SGX/HSM "Lockbox" enclave ([github.com/commerceblock/lockbox](https://github.com/commerceblock/lockbox) — link now dead, see below).
- **Lessons.** An independent audit (published 2024-10-31) found five vulnerabilities — two high-severity enabling **instant theft/double-spend** (unvalidated locktimes, sequence numbers) plus sighash-flag poisoning — and stressed that blind signing made server-side validation impossible, while a malicious server could always collude with a past owner regardless ([conduition.io](https://conduition.io/code/mercury-disclosure/)). Both Mercury generations saw only marginal real-world use ([bitcoinmagazine.com](https://bitcoinmagazine.com/technical/bitcoin-layer-2-statechains)).
- **Status: defunct.** CommerceBlock "shuttered its doors" (noted May 2025, [bitcoinmagazine.com](https://bitcoinmagazine.com/builders/bitcoin-builders-exist-because-of-users)); as of 2026-06-12 the `commerceblock` GitHub org returns **0 public repos** (repos deleted/private; verified via GitHub API). Earlier "active as of Jan 2025" claims rest on stale caches.

## 2) Spark (Lightspark)

- **History.** Announced Oct 2024 ([lightspark.com](https://www.lightspark.com/news/spark/introducing-spark), [nobsbitcoin.com](https://www.nobsbitcoin.com/lightspark-introduces-spark/)); mainnet beta 2025; a16z-backed; repositioned in 2025–26 as a "payments + stablecoins on Bitcoin" L2 ([spark.money](https://www.spark.money/research/what-is-spark-bitcoin-layer-2)).
- **Statechain transfers (key tweak).** A deposit UTXO is locked to a combined key `PubKey_user + PubKey_SE` (SE = Spark Entity). On transfer, the SE **additively tweaks its share by the difference between sender and receiver keys**, preserving the combined key (`PubKey_sender + PubKey_SE = PubKey_receiver + PubKey'_SE`), co-signs the receiver a new exit tx with a **lower timelock**, and **deletes the old share** — the key-deletion assumption: forgetting must actually happen for the sender's share to become useless ([docs.spark.money/learn/transfers](https://docs.spark.money/learn/transfers), [technical-definitions](https://docs.spark.money/learn/technical-definitions)).
- **Trees, leaves, denominations/change.** Deposits form a tree; **leaves** are user-owned terminal nodes. Leaves split via key arithmetic (`a0 = a1 + a2`) into smaller denominations off-chain; SSPs keep inventory in **power-of-2 denominations**, and the SDK does **leaf swaps with the SSP** when no exact-amount leaf exists (change handling) ([docs.spark.money/learn/core-concepts](https://docs.spark.money/spark/core-concepts), [technical-definitions](https://docs.spark.money/learn/technical-definitions)).
- **Operators & threshold signing.** The SE is a federation of Spark Operators (SOs) signing via **FROST** with a configurable t-of-n threshold. As of 2025–26 only **two SOs: Lightspark and Flashnet**, with expansion "planned" ([panewslab.com](https://www.panewslab.com/en/articles/4uznhoso), [docs.spark.money/home/beta-details](https://docs.spark.money/home/beta-details)).
- **SSPs.** Spark Service Providers (first one run by Lightspark) handle cooperative deposits/withdrawals, leaf-denomination swaps, and Lightning ([docs.spark.money/learn/core-concepts](https://docs.spark.money/spark/core-concepts)).
- **Lightning interop.** No channels/nodes for users. Send: SE conditionally locks the user's leaves; SSP pays the invoice, presents the preimage/proof, SE atomically finalizes leaf transfer to the SSP; on timeout, leaves unlock back to the user. Receive: **preimage shards held across operators** ("preimage swap"), released atomically under the same honest-minority assumption ([docs.spark.money/learn/lightning](https://docs.spark.money/learn/lightning)).

## 3) The "operator must forget old key shares" problem & mitigations

- **The problem.** Deletion is unprovable: a retained share + past owner = theft from the current owner; users "are unable to have any finality assurances" ([bitcoinlayers.org/layers/spark](https://www.bitcoinlayers.org/layers/spark), [bitcoinmagazine.com](https://bitcoinmagazine.com/technical/trustodial-an-ontological-dilemma)).
- **Known mitigations:**
  - **Threshold federation (Spark):** deletion duty spread over n operators; one honest deleter breaks reconstruction. Caveat: with a t-of-n *signing* threshold, t colluding retainers can sign, so the 1-of-n claim is strongest at n-of-n tweaking; Spark's docs themselves say "one honest operator *(or configurable threshold)*" ([docs.spark.money/learn/trust-model](https://docs.spark.money/learn/trust-model)).
  - **Trusted hardware + remote attestation (Mercury Lockbox, SGX/HSM):** semi-proves deletion but shifts trust to Intel/vendor ([bitcoinmagazine.com](https://bitcoinmagazine.com/technical/trustodial-an-ontological-dilemma)).
  - **Blind co-signing (Mercury Layer):** operator can't see what it signs, hindering *targeted* collusion — but the 2024 audit showed it also blocks server-side validation and doesn't fix deletion ([conduition.io](https://conduition.io/code/mercury-disclosure/)).
  - **Decrementing-timelock exit txs:** current owner can always confirm first on L1 — protects against old-owner-alone, not operator+old-owner collusion ([docs.spark.money/learn/technical-definitions](https://docs.spark.money/learn/technical-definitions)).
  - **Proactive resharing** of federation shares (invalidates *exfiltrated* old shares; doesn't stop deliberate retention) — discussed in statechain literature/Spark design docs but not verifiably deployed as of mid-2026.
  - **Reputation/legal accountability:** identified, regulated operators (Lightspark, Flashnet) risking business destruction ([bitcoinlayers.org](https://www.bitcoinlayers.org/layers/spark)). No classical cryptographic proof-of-deletion exists.

## 4) Spark's stated trust assumptions vs. criticisms

- **Spark says:** "1-of-n," "moment-in-time" trust, "perfect forward security" if shares are forgotten; funds "always non-custodial" with unilateral L1 exit depending "on Bitcoin and no one else" ([docs.spark.money/learn/trust-model](https://docs.spark.money/learn/trust-model), [spark-tldr](https://docs.spark.money/spark/spark-tldr)).
- **Critics say:** deletion is unverifiable, so the non-custodial label is contestable — Shinobi's "Trustodial" essay (2025-07-07, triggered by Wallet of Satoshi's Spark-based US relaunch) argues it's neither provably custodial nor non-custodial ([bitcoinmagazine.com](https://bitcoinmagazine.com/technical/trustodial-an-ontological-dilemma)). Bitcoin Layers flags unprovable keyshare deletion and weak finality ([bitcoinlayers.org](https://www.bitcoinlayers.org/layers/spark)). Seth For Privacy (2025-10-23) adds: only two operators; all operators see all transactions (Flashnet publishes them via Sparkscan); **static addresses** make privacy "worse than on-chain"; default SDKs leak Spark addresses inside Lightning invoices ([bitcoinmagazine.com](https://bitcoinmagazine.com/technical/spark-and-ark-a-look-at-our-newest-bitcoin-layer-twos)).

## 5) Adoption, incidents, open vs. proprietary

- **Adoption (2025–26):** Breez SDK (May 2025) and Wallet of Satoshi "self-custodial" relaunch (July 2025); Xverse (~1.6M users), Magic Eden settlement, Privy wallet infra; Brale's **USDB** — first regulated stablecoin native on Spark; Flashnet DEX/Sparkscan; Q2-2026 roadmap: cheap BTC on-ramps, cross-chain swaps, stablecoin yield ([lightspark.com](https://www.lightspark.com/news/spark/breez-spark-partnership), [coinedition.com](https://coinedition.com/xverse-integrates-spark-unlocking-instant-bitcoin-defi-and-stablecoins-for-1-6-million-users/), [lightspark.com](https://www.lightspark.com/news/spark/magic-eden-spark-partnership), [crowdfundinsider.com](https://www.crowdfundinsider.com/2026/01/257366-bitcoin-l2-protocol-spark-unveils-q2-2026-roadmap/)). Don't confuse with Sky/MakerDAO's Ethereum "Spark" ($12B+ TVL — different project).
- **Incidents:** no publicly reported Spark theft/outage found as of 2026-06-12 (absence of evidence, not proof). Mercury's audit findings (above) predate its shutdown.
- **Open vs. proprietary:** [github.com/buildonspark/spark](https://github.com/buildonspark/spark) (Apache-2.0) contains the Go operator, Rust FROST signer, JS SDKs, protobuf specs; actively developed. The **SSP is closed** — community notes there's "no clear way to run an SSP without a business relationship with Lightspark" ([issue #64](https://github.com/buildonspark/spark/issues/64)).

## 6) Receive-while-offline

- **Spark-native transfers:** asynchronous — sender + SE complete the tweak/lock; the recipient need not be online and claims the pending transfer later; unclaimed transfers revert after timeout ([spark.money](https://www.spark.money/research/what-is-spark-bitcoin-layer-2), [docs.spark.money/learn/transfers](https://docs.spark.money/learn/transfers)).
- **Lightning receives:** work offline via operator-held preimage shards under the same honest-minority assumption — a headline differentiator vs. vanilla Lightning for mobile wallets ([docs.spark.money/learn/lightning](https://docs.spark.money/learn/lightning), [bitcoinmagazine.com](https://bitcoinmagazine.com/technical/spark-and-ark-a-look-at-our-newest-bitcoin-layer-twos)).
- **Trade-off:** offline receive deepens reliance on the SE/SSP being live and honest at claim time; unilateral exit still requires the user (or a watchtower) to eventually come online before timelocks matter.
